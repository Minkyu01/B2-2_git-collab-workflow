# 팀 가이드

B2-2 「실전 Git 협업 워크플로우」를 셋이 진행하는 순서와, 평가 때 설명할 내용을 모았다. AI 에이전트용 작업 지시서는 [AGENTS.md](../AGENTS.md)다.

## 이 과제는

만드는 것은 거의 없다. 셋이 이슈 → 브랜치 → PR → 리뷰 → 병합을 실제로 주고받고, 일부러 충돌을 내 풀고, 실수를 되돌리는 명령 네 가지를 써 보고, 그 과정을 GitHub 기록과 문서로 남기면 된다. 평가자는 저장소를 열어 그 기록을 세고, 왜 그렇게 했는지 말로 묻는다.

| 1인당 기준 | 수 |
| --- | --- |
| PR 만들어서 병합 | 2개 이상 |
| 다른 사람 PR 리뷰 | 2개 이상 |
| 내 PR에서 리뷰 반영 | 1회 이상 |
| 실습 기록 참여 | 1개 이상 |
| 팀 소개 커밋 | 1건 이상 |

팀 전체로는 PR마다 이슈 연결, PR마다 실질 리뷰 코멘트, 충돌 해결 2회(그중 비자명 1회 이상), 실습 4종(amend, reset, revert, stash), 문서 3종(CONTRIBUTING, 충돌 기록, 실습 기록), `SUBMISSION.md`가 필요하다.

## AI로 진행하는 법

1. 저장소를 clone하고, 쓰는 AI 에이전트(Codex, Claude Code, Cursor 등)를 저장소 폴더에서 연다.
2. 이렇게 말한다: **"AGENTS.md 읽고 다음 내 차례 진행해"**
3. AI가 멈추고 묻는 곳에서만 확인한다: 자기소개 내용, 리뷰 코멘트 문구, 승인, 병합, 충돌을 정리한 결과.
4. 단계가 끝나면 AI가 주는 "팀 채팅 한 줄"을 팀 채팅에 보낸다. 다음 사람은 그걸 보고 움직인다.
5. AI가 단계마다 해 주는 설명(무엇을, 왜, 평가에서 어떻게 말할지)을 읽는다. 평가 때는 AI 없이 직접 설명해야 한다.

## 차례표

같은 줄에 있는 일은 동시에 해도 된다. 관문은 셋 다 넘어야 다음으로 간다.

| 단계 | 유민규 | 신은영 | 민영재 |
| --- | --- | --- | --- |
| 준비 | 저장소·main 보호·안내 자료·초대 | | |
| 0 | 합류 | 합류 | 합류 |
| **관문 A** | 셋 다 "준비 완료" | | |
| 1~3 | PR1 열기: CONTRIBUTING 1·2·7절 + amend | PR1 열기: 3·4절 + reset, PR2 시작만 | PR1 열기: 5·6절 |
| 4 | 영재 PR1 리뷰 | 민규 PR1 리뷰 | 은영 PR1 리뷰 |
| 5 | 반영 + 답글 | stash로 반영 + 답글 | 반영 + 답글 |
| 6 | 승인하고 내 PR 병합 | 승인하고 내 PR 병합 | 승인하고 내 PR 병합 |
| **관문 B** | PR1 셋 다 병합 | | |
| 7~8 | PR2 열기 (병합 금지) | | PR2 열기 (병합 금지) |
| **관문 C** | 영재·민규 PR2가 열려 있음 | | |
| 9 | 은영 PR2 리뷰·승인 | PR2 열기 → 병합 ④ | |
| 10 | | 영재 PR2 리뷰·승인 | main 받기 → 충돌 #1 → 병합 ⑤ |
| 11 | main 받기 → 충돌 #2 → 병합 ⑥ | | 민규 PR2 리뷰·승인 |
| 12 | 영재 PR3 리뷰·승인 | | TMI 커밋 revert → 병합 ⑦ |
| 13 | SUBMISSION → 병합 ⑧ | 민규 PR3 리뷰·승인 | |
| 14 | 설명 연습 | 설명 연습 | 설명 연습 |

PR2 병합 순서 ④ 은영 → ⑤ 영재 → ⑥ 민규는 바꾸지 않는다. 이 순서여야 충돌이 계획한 곳에서 난다.

## 설명 카드

### 과제 목표 6가지

| 주제 | 이렇게 설명한다 | 보여 줄 것 |
| --- | --- | --- |
| 브랜치의 정체 | 브랜치는 커밋 하나를 가리키는 이름표다. 커밋하면 그 이름표가 새 커밋으로 옮겨 간다. 만들고 지우는 비용이 거의 없어서, 각자 자기 이름표만 움직이며 main을 건드리지 않고 일한다. | `git rev-parse main`, `git log --oneline --graph --all` |
| GitHub Flow | main 하나와, 작업마다 만드는 feature 브랜치뿐이다. 작업이 끝나면 PR로 리뷰를 받고 main에 합친다. 셋이 작은 작업을 자주 합치는 규모라 develop·release 브랜치가 필요 없다. | `docs/CONTRIBUTING.md` 1절 |
| PR과 리뷰 | 병합 전에 다른 사람이 한 번 더 본다(품질). 누가 승인했는지 남는다(책임). 이슈·토론·커밋이 한곳에 모여 나중에 이유를 찾을 수 있다(추적성). | 리뷰 코멘트가 달린 PR |
| 충돌과 마커 | 두 사람이 공통 조상에서 같은 곳(붙어 있는 줄 포함)을 다르게 고치면 Git이 어느 쪽을 택할지 모른다. `<<<<<<< HEAD`부터 `=======`까지는 지금 내 브랜치, `=======`부터 `>>>>>>> origin/main`까지는 합치려는 쪽이다. | `docs/conflict-resolution.md` |
| reset · revert · stash | reset은 브랜치를 과거 커밋으로 되돌려 히스토리를 고쳐 쓴다(push 전에만). revert는 변경을 거꾸로 하는 새 커밋을 더한다(push 후). stash는 커밋하지 않은 변경을 잠깐 치워 둔다. | `docs/troubleshooting-log.md` |
| 재현 가능한 기록 | 상황, 실제로 친 명령과 출력, 결과, 주의점, 그 방법을 고른 이유를 남긴다. 리뷰어가 기록대로 다시 해 보고 확인했다. | 기록 문서의 각 절 |

### 우리가 한 실습

| 실습 | 누가 | 이렇게 설명한다 |
| --- | --- | --- |
| amend | 유민규 | push하기 전에 마지막 커밋 메시지가 규칙 위반(`docs: update`)인 걸 보고 `--amend`로 고쳤다. 커밋을 새로 만들어 바꿔치기해서 해시가 바뀐다. 그래서 push한 뒤에는 쓰지 않는다. |
| reset --soft | 신은영 | 개인 메모까지 같이 커밋해서, `reset --soft HEAD~1`로 커밋만 풀고 변경은 스테이징에 남겼다. 메모만 빼고 다시 커밋했다. `--hard`였다면 변경까지 사라진다. |
| stash | 신은영 | PR2를 쓰는 중에 PR1에 리뷰가 와서, 커밋하지 않은 작업을 stash로 치우고 PR1을 고친 뒤 돌아와 pop했다. 새 파일은 `-u`를 붙여야 같이 보관된다. |
| revert | 민영재 | 이미 main에 들어간 TMI 섹션 커밋을 revert로 되돌렸다. 원래 커밋은 남고 반대 커밋이 더해져서, 팀원은 pull만 하면 된다. reset으로 지웠다면 팀원들 main과 갈라지고 강제 push가 필요한데, 보호된 main은 그걸 거부한다. |
| 충돌 #1 | 민영재 (상대 신은영) | 은영과 내가 README 팀원 표의 붙은 줄을 각각 고쳤다. 은영 PR이 먼저 병합된 뒤 main을 받아오자 충돌이 났다. 두 줄 다 살리는 쪽으로 풀고 `git diff --check`로 마커가 남지 않았는지 확인했다. 인접한 줄을 서로 다르게 고친 경우라 비자명 충돌이다. |
| 충돌 #2 | 유민규 (상대 민영재) | 영재는 임시 메모 파일을 지웠고, 나는 같은 파일에 한 줄을 더해서 modify/delete 충돌이 났다. 원래 다 쓰면 지우기로 한 파일이라 삭제를 받아들이고, 내가 더한 규칙은 `team/README.md`로 옮겼다. 한쪽 삭제와 다른 쪽 수정이라 비자명 충돌이다. 이 충돌은 GitHub 웹 편집기로 못 풀어 로컬에서 풀었다. |

파일 이름만 바꾸고 다른 쪽이 내용을 고치면 Git이 이름 변경을 알아채 충돌 없이 합친다. 그래서 두 번째 충돌은 삭제로 냈다.

### 평가에서 말로 묻는 것 (줄여 씀)

| 질문 | 핵심 답 |
| --- | --- |
| 작업 단위는 어떻게 나눴나 | 이슈 1개 = 브랜치 1개 = PR 1개. PR 하나는 목적이 하나다. |
| PR 본문에 What·Why·How와 이슈를 빠짐없이 넣으려고 무엇을 썼나 | `.github`의 PR 템플릿과 이슈 템플릿, 그리고 리뷰어가 본문 칸도 확인했다. |
| 리뷰가 LGTM으로 끝나지 않게 어떻게 했나 | 줄 코멘트 1개 이상 규칙, 말머리 네 가지, 답글이 달린 뒤에만 승인, 리뷰 순번표. |
| 충돌이 나면 어떻게 했나 | 충돌 난 PR 작성자가 공유하고, 자기 브랜치에서 main을 받아 풀고, 상대가 리뷰하고, 기록 문서에 남겼다. |
| 기록을 재현 가능하게 만든 방법은 | 참여자, 상황, 실제 명령과 출력, 결과, 주의점, 이유를 매번 같은 칸에 썼다. |
| main을 항상 배포 가능하게 두는 이유는 | 모든 새 작업이 main에서 출발한다. main이 깨지면 그 뒤 브랜치가 모두 깨진 채 시작한다. |
| main에 직접 push하지 않고 PR과 승인으로 합치는 이유는 | 품질, 책임, 추적성. 그리고 보호 규칙으로 강제했다 (main에 직접 push하면 GH006으로 거부된다). |
| 이슈와 PR을 잇는 이유는 | 왜(이슈)와 어떻게(PR)가 연결되고, 담당이 보여 중복 작업을 막고, `Closes #`로 병합 때 이슈가 자동으로 닫힌다. |
| push한 커밋을 되돌릴 때 reset 대신 revert를 쓰는 이유는 | reset은 이미 팀원이 받아 간 커밋을 지워 히스토리가 갈라지고 강제 push가 필요하다. revert는 새 커밋을 더할 뿐이라 안전하다. |
| 충돌 마커의 뜻과 비자명 충돌을 풀 때의 기준은 | 마커 뜻은 위 카드. 기준은 양쪽 PR의 의도를 먼저 확인하고, 둘 다 살릴지·하나를 고를지·새로 쓸지 정하고, 상대 내용을 버리면 먼저 이야기하는 것. |
| main에 급한 수정이 필요하면 | 이슈 → main에서 `feature/<아이디>-hotfix-…` → 최소 수정 → PR과 빠른 리뷰(승인 규칙은 그대로) → 병합. 직전 PR이 원인이면 그 PR을 revert하는 PR이 더 빠르다. |
| 의미 없는 커밋 메시지가 여러 개 push됐다면 | 병합 전이든 후든 고쳐 쓰지 않는다(강제 push 금지). 다음 커밋부터 규칙을 지키고, PR 제목과 본문으로 무엇을 했는지 추적하게 하고, 규칙·템플릿·리뷰로 재발을 막는다. |
| 같은 곳에서 충돌이 반복되면 | 원인은 여럿이 같은 목록 파일을 고치는 구조, 오래 열어 둔 브랜치, 큰 PR. 사람별 파일로 나누고, PR을 작게, main을 자주 받는다. |
| (보너스) rebase가 협업에서 위험한 이유는 | 커밋을 새로 만들어 해시가 바뀌므로, 이미 받아 간 사람과 히스토리가 갈라지고 강제 push가 필요하다. 혼자 쓰는 브랜치에서만, 백업 브랜치를 만들고, `--force-with-lease`로. |
